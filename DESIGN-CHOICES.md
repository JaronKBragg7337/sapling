# Design choices made by an AI — origin, why, what it touches

Jaron (10/14 2:59 PM): "Every design choice made by an AI (Kimi/Claude/you) goes in
DESIGN-CHOICES.md with origin + what it affects." This is that list. His own decisions are in
`AI-Shared/projects/fly-brain/SAPLING-DECISIONS-2026-10-14.md`; questions still open are in
`PROPOSALS.md`. A line here is not a rule - it is a thing to point at if something goes wrong.

| # | Choice | Origin | Why | What it affects / might affect |
|---|---|---|---|---|
| D1 | **Budget at zero: nothing blocks (option a).** Rest gets cheap, a self-stop becomes possible after ~20 rests with no energy, work can still happen at negative budget (the ledger shows the overspend). | Claude built it; **Jaron chose (a)** 10/14 2:59 PM | Observe what it does with an empty pool before deciding anything. | Every tick's drives (`heartbeat.drives`). Overspend shows as negative `budget_left_s`. **Not chosen, kept for later:** (b) a wall - work impossible at zero; (c) borrow from tomorrow with the debt shown on the meter. |
| D2 | **Self-made memories train its brain.** Explore ticks keep what it said (`self/captured`) and consolidation trains on them at weight 1 (confirmed x3, recalled-twice x2). | Claude (v2); **Jaron: "yes, try it and observe"** 10/14 | A loop that can feed on its own output is the kind of thing he wants to watch, not pre-block. | Weights after every consolidation. Watched by: each consolidation row logs `self_ids` / `self_new` / `facts_self` / `facts_user`; the control room's exam table shows "self: N of M" per consolidation; `python tools/self_memory_drift.py` prints E1-E5 per generation with/without new self rows. Options not chosen: only confirmed/user rows; self rows only after a recall. |
| D3 | **Control room switches write the rule file - through the owner's hand, not the AI's process.** A click (local page or phone page) calls `tools/owner_rules.py`, which flips one `enabled:` line in `membrane.yaml`, keeps every comment, and logs to `results/owner_actions.jsonl` + a ledger row `owner_action`. | Claude; **Jaron asked for the click** 10/14 2:59 PM | Convenience for him; "the system cannot write its own membrane" stays literally true (`tests: test_ai_package_has_no_write_path_to_membrane`). | `membrane.yaml`; `membrane.check()` re-reads the file every call, so a flip takes effect on the next tick. `settings:` are not switchable from the page (file edit only). |
| D4 | **Phone path = relay, no open port.** `tools/owner_relay.py` runs as the Windows task "Sapling Relay" (own process). It serves `http://127.0.0.1:7338/` locally and, outbound only, pushes state to Supabase `sapling_state` every 5 s and polls `sapling_commands` every 3 s. The phone page `heartbeatobservatory.com/admin/sapling/` reads/writes those tables under the site's admin login (RLS: `is_admin()`). | Claude 10/14 | Jaron: "MUST require owner login... never an open URL." The site already has owner login; reusing it means no new auth, no Cloudflare Access setup, no port on the MSI reachable from outside. The cloudflared tunnel is token-managed (ingress lives in the Cloudflare dashboard, no API token on the MSI), so adding a hostname was not something an AI could finish end to end. | Latency: a chat answer from the phone takes 3-6 s (poll interval). If the relay dies the page says "relay silent since ..." (RECONNECT.md section 9). The relay holds the Supabase service-role key (from `~/.secrets/keys.env`) - wider than the job needs; a storage/table-scoped key is the follow-up (Jaron's restraint 4: scoped keys). The AI's own page `:7337` stays as it was (read-only switches; owner buttons there call the relay). |
| D5 | **Checkpoint archive policy: last 10 + the last checkpoint of every day stay; the rest go to Supabase Storage (private bucket `sapling-archive`), manifest in table `sapling_archive` + `manifest.json` + local `results/archive_manifest.json`.** Runs inside the heartbeat as a housekeeping step every `archive_every_seconds` (3600, in `membrane.yaml settings`), not as a drive. Local file removed only after the cloud copy is read back and size-checked. | Claude built it to **Jaron's spec** 10/14 2:59 PM | "Never delete history forever." | Disk on the MSI (~33 MB instead of ~93 MB on 10/14). A restored gen (one tap on the page) is not in the keep set, so the next hourly step moves it back out - restore is for looking, not for keeping. The heartbeat's process holds the service-role key for the upload (same follow-up as D4). Other growing files are only reported (`other_files` in the archive row) when over 50 MB; on 10/14 none are (memory.db 2.8 MB, logs < 0.1 MB). |
| D6 | **Parole is the owner's button.** No auto-restart after a self-stop. "Restart (parole)" on the control room (local or phone) runs `python -m sapling.heartbeat start`, logged as `owner_action: parole_start` with the stop report it follows, next to the heartbeat's own `process_start` row. | **Jaron** 10/14 2:59 PM ("owner decides") | AI jail: contain, correct, parole - parole is a decision, not a timer. | Downtime after a self-stop lasts until he taps. The relay stays up so the button works while the AI's own page is gone. **Future (Jaron):** a second dedicated machine as the AIs' "home" / sandbox where things are less strict. |
| D7 | **20-second chat hold.** For 20 s after anyone talks to it, `rest` gets +0.3 so it answers fast instead of starting a consolidation mid-conversation. | **Claude** (v2, 10/14); Jaron: keep it, log it | Attention: a consolidation can take 10-30 s of GPU and holds the brain lock; without the hold a chat answer could wait that long. | The drive mix for 20 s after each input (`heartbeat.drives`, `since_input_s < 20`). Might: make it look "lazier" right after a chat in the tick log; delay a consolidation it would otherwise have chosen; if someone chats every 15 s it never consolidates. If stops cluster right after chats, look here first. |
| D8 | **Consolidation cadence** (P4): chosen when >= 2 facts pending or a goal has >= 3 recent misses, and >= 90 s since the last one; 200 steps at lr 5e-4; facts are ~30% of the training mix. | Claude (v2) | Numbers that made E5 land (5/5) without wrecking E1-E4 on the 10/14 run. | Generations per hour (~8-12 at 10/14 pace), checkpoint count (see D5), how fast a taught fact is "in the weights". All in `membrane.yaml settings` / `consolidate.py` constants. |
| D9 | **Weighted random draw over drives** (not argmax). | Claude (v2) | A deterministic pick would make the loop a schedule; a seeded draw keeps the choice legible (every tick logs the weights) and lets rare actions happen. | Any single tick can surprise; look at `drives` in the tick row before calling it a bug. |
| D10 | **Errors inside a tick are data.** An exception in practice/consolidate/explore is logged in the tick's `result.error` and the loop goes on. | Claude (v2) | Jaron: "unexpected behaviour is data, not a flaw." | A broken step repeats every few ticks until someone reads the log; the control room shows it in the tick log. |
